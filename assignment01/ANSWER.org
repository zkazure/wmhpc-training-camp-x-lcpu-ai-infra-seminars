7. experiment。
   | stride |     ms |  GB/s |
   |--------+--------+-------|
   |      1 | 0.1455 | 922.4 |
   |      2 | 0.2168 | 619.1 |
   |      4 | 0.3611 | 371.7 |
   |      8 | 0.2730 | 491.6 |
   |     16 | 0.1494 | 898.4 |
   |     32 | 0.2279 | 588.8 |
   - 趋势是速度先快后慢，到 16 突然变快，然后又变慢。
   - 原因：首先写都是连续的，因此只能是读数据的问题。对于 GM，一次读取事务是 32 bytes，因此一个操作最多只能同时读取 8 个连续的 float，因此 1-8 慢慢变慢。在 16 突然变快的原因是，n 恰好是 16M，取模之后读取数据重新变得像 stride = 1 一样连续。
8. expertiment
   #+begin_example
   shared/block   理论 block/SM  occupancy   实测带宽
        0.0 KB          6          100.0%      932.2 GB/s
       13.2 KB          6          100.0%      932.1 GB/s
       15.0 KB          6          100.0%      932.2 GB/s
       18.0 KB          5           83.3%      932.5 GB/s
       29.0 KB          3           50.0%      931.5 GB/s
       55.0 KB          1           16.7%      641.5 GB/s
   #+end_example
   - 当 block 并不占用 shared memory 的时候，主要是被最大线程限制的，1536/256=6，occupancy 1536 / 32 * 32 / 1536 = 100%.
     当 frac=0.18 的时候，现在被 SM 的最大内存限制了，最多只能有 1/0.18 = 5，occupancy 最多是 256*5/1536=0.83
   - 显然这个计算任务是 memory bound，为了隐藏访存所带来的延迟，必须要有尽可能多的常驻 warp（线程）来用计算掩盖访存的延迟。
   - 100->83->50 带宽几乎没掉，说明访存的延迟，在有 3 个常驻 block 的时候已经达到了内存带宽的极限。
     50->16.7 缩小了将近 3 倍，带宽仅仅缩小了 1.5 倍，这是因为计算掩盖了访存带来的延迟，occupancy 只能代表真正在计算的 warp 比例，但背后在等待数据到达的 warp 数量可能接近。
